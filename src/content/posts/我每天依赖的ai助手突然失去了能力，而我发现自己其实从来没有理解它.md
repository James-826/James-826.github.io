## 晚上八点

2026年8月6日，农历六月廿四。

这本来应该只是一个再普通不过的夜晚。

结束了一天紧张的“三角洲行动”。之后，我终于迎来了属于自己的时间。

白天，我需要面对三角洲世界里的各种任务；而到了晚上，我会打开电脑，进入另一个世界。

对很多人来说，一天结束后的奖励可能是一部电影，或者一顿美食。

但对我来说，最期待的时刻，是打开 Codex。

看着终端里那个熟悉的窗口出现，然后告诉它：

“帮我看看这个问题。”

或者：

“我们试试做一个新的小玩意。”

那一瞬间，总有一种奇怪的满足感。

像是一个刚刚结束冒险的玩家，终于回到了自己的基地。

我喜欢这种感觉。

不是因为 AI 能替我完成多少工作，而是因为在这个过程中，我总能不断发现新的东西。

代码、工具、框架、协议……

那些原本隐藏在计算机世界深处的结构，会一点一点展现在我面前。

所以每天晚上打开 Codex，几乎已经成为了一种习惯。

只是我没有想到。

今晚的 Codex，好像有一点不太一样。

我输入需求之后，它没有像往常一样直接开始工作。

反而停了下来。

“为了更好地完成这个任务，我想先确认一下……”

紧接着，一个又一个问题出现在屏幕上。

一开始，我甚至有点欣慰。

“不错呀，终于开始认真思考我的需求了。”

以前的 Codex 更像一个执行力很强的工程师，我告诉它目标，它就直接开始行动。

而今晚的它，更像一个刚入职的新人。

谨慎、认真、反复确认每一个细节。

甚至有那么一瞬间，我觉得它是不是进化了。

也许它终于学会了理解用户，而不是简单执行指令。

作为一个长期使用它的人，我甚至产生了一种奇怪的欣慰感。

“孩子长大了。”

“知道先理解爸爸的需求了。”

我就这样看着它一次次询问，然后耐心回答。

一次。

两次。

三次。

……

直到第五次。

我突然意识到，好像哪里不对。

这已经不是认真了。

它似乎陷入了某种循环。

它越来越会聊天。

但它始终没有开始工作。

## 第一个嫌疑人

我开始寻找第一个嫌疑人。

程序员遇到问题的时候，总会有一种条件反射：

“是不是我刚刚改了什么？”

最近安装的 skills 第一个进入了我的怀疑名单。

毕竟，一个突然变得奇怪的 AI 助手，很可能不是它自己的问题，而是我偷偷给它增加了什么东西。

于是我关闭了最近启用的 superpowers。

重启。

再次尝试。

然而，屏幕上的结果并没有改变。

它依然在那里反复确认。

依然没有开始执行。

直到下一秒，我发现了真正让我感到不安的事情。

我的 Codex，失去了调用工具的能力。

难道是我穿越到了异世界？一觉醒来全世界的codex都不变，只有我无法调用工具？

那一刻，心里突然空了一下。

因为对于现在的我来说，Codex 已经不只是一个聊天窗口。

它更像一个可以一起探索未知世界的伙伴。

如果它不能调用工具，那它就像一个失去了双手的人。

我甚至不敢想象：

“没有 Codex 的日子，我该怎么办？”

## 先从搜索开始

当然，恐慌只持续了一分钟。

作为一个程序员，我很快恢复理智。

遇到问题，第一反应永远不是放弃。

而是搜索。

于是我打开了那个程序员们寻找答案的地方。

果然，我并不是唯一一个遇到这个问题的人。

很多开发者都在讨论类似的问题。

其中，一个编号为 #3487 的 issue 引起了我的注意。

我点进去。

然后……

沉默了。

里面讨论的内容，全部都是一些我看不懂的技术细节。

什么协议转换。

什么消息格式。

什么工具调用。

什么接口兼容。

看着这些内容，我突然意识到一个尴尬的事实：

我每天都在使用 CC Switch。

配置好地址。

选择模型。

点击启动。

然后享受它带来的便利。

它确实很好用。

好用到让我忘记了一件事情：

我从来没有真正理解过，它到底是怎么工作的。

## 重新认识 CC Switch

那一刻，我决定重新认识一下这个每天都在使用的工具。

CC Switch。

我打开资料之前，对它的理解其实非常简单。

在我的脑海里，它大概就是一个“配置管理器”。

改一下 config。

换一下 API 地址。

选择一个模型。

然后继续使用。

就像给汽车换了一条道路。

我只需要告诉它：

“我要去哪里。”

至于中间经过什么地方，并不重要。

至少以前我是这么认为的。

但是当我真正开始了解它之后，我发现自己想得太简单了。

CC Switch 并不是简单地修改配置。

它更像是一个站在 Agent 和模型之间的翻译官。

当 Codex 发出请求时，它不会直接到达最终模型。

请求会先经过 CC Switch。

在这里，它会根据当前配置进行路由选择：

应该发送给哪个上游？

应该使用哪个模型？

应该转换成什么协议格式？

这些事情，全部发生在中间这一层。

更有意思的是，这个过程对于 Agent 本身几乎是透明的。

Codex 仍然认为自己正在和熟悉的接口通信。

它不知道自己的请求已经经过了一次“旅行”。

从一种协议。

转换成另一种协议。

再发送给另一个模型。

最后，上游返回结果之后，CC Switch 又会把响应重新转换成 Codex 能理解的格式。

然后交还给 Agent。

就像一个同声传译。

两个人在对话。

但他们中间有一个翻译。

双方都不知道对方原本使用什么语言。

而我之前，就是那个只享受翻译结果的人。

我从来没有想过：

在我的 AI 助手能够正常工作的背后，还有这样一个隐藏的中间世界。

但是，当我继续思考 CC Switch 的设计时，一个更加熟悉的感觉慢慢浮现出来。

因为我突然发现：

它解决的问题，和我之前开发 Agent 时遇到的问题，本质上是一样的。

那就是：

如何让上层逻辑，不依赖底层具体实现。

### 在 Agent 内部抽象模型

在开发自己的 Agent 框架时，我也遇到过类似的问题。

如果 Agent 的核心循环直接绑定某一家模型，那么整个系统会变得非常脆弱。

今天使用 OpenAI。

明天想换 Claude。

后天想接入其他供应商。

难道每换一个模型，就需要重新修改 Agent 的核心逻辑吗？

显然不是。

所以当时我的思路是：

使用面向接口编程。

我先定义了一个统一的 Provider 基类。

让 Agent 不关心背后到底是哪一个模型。

它只需要知道：

“我调用 complete，然后获得一个标准结果。”

例如，Provider 可以只暴露一个统一的 `complete` 方法：

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass
class ModelResult:
    text: str | None = None
    tool_calls: list[dict] | None = None


class Provider(ABC):
    @abstractmethod
    def complete(self, messages: list[dict]) -> ModelResult:
        raise NotImplementedError
```

然后，我又定义了统一的返回协议。

因为不同模型返回的数据结构并不完全一样。

有的模型返回文本。

有的模型返回工具调用。

有的模型工具调用字段名称甚至不同。

所以我把它们统一抽象成自己的格式：

```python
result = ModelResult(
    text="我需要先读取项目文件。",
    tool_calls=[
        {
            "id": "call_001",
            "name": "execute_command",
            "arguments": {"cmd": "ls -la"},
        }
    ],
)
```

其中工具调用可以统一成三个核心字段：

```python
tool_call = {
    "id": "call_001",
    "name": "execute_command",
    "arguments": {"cmd": "ls -la"},
}
```

这样，在 Agent Loop 中，我不需要知道：

现在回答我的到底是 GPT，还是 Claude。

我只需要处理统一的数据结构：

对于 Agent 来说，模型只是 Provider 后面的一个黑盒。

如果未来增加新的供应商，我只需要新增一个 Provider：

Agent 的核心循环完全不需要修改。

但是，当我看到 CC Switch 的设计之后，我发现了一种更加底层的解耦方式。

我的方案，是在 Agent 内部抽象模型。

而 CC Switch，则是在 Agent 外部抽象协议。

它并不关心 Agent 为什么调用模型。

它只关心：

“你说的是哪一种语言？”

“我应该如何把它翻译成另一种语言？”

所以它不需要为每一个模型写完整的 Provider。

而是通过协议转换，让不同生态之间能够连接。

比如，客户端只需要配置统一的入口地址：

```python
import os


client_config = {
    "base_url": os.getenv("CC_SWITCH_BASE_URL", "http://127.0.0.1:15721/v1"),
    "model": "upstream-model",
}
```

从这个角度看，CC Switch 更像一个翻译官。

Agent 只需要使用自己熟悉的语言。

后面的模型是什么语言，由它负责转换。

这也是为什么它能够让上层应用几乎无感地切换不同模型入口。CC Switch 的接入方式本身也是通过调整 `BASE_URL` 等配置，让客户端保持原有调用方式，再由中间层处理请求转发和兼容。

### 抽象层的代价

但是，所有抽象层都有自己的代价。

Provider 模式的问题是：

- 每增加一种模型，就需要维护一个新的适配器。

而协议转换模式的问题是：

- 所有模型之间的差异，都集中到了转换层。

一旦转换逻辑出现错误。

或者协议理解出现偏差。

那么整个调用链都会受到影响。

这也是为什么，当我再次回头看 #3487 这个 issue 时，我第一次真正理解了它的问题所在。

它并不是简单的“工具调用失效”。

而是一场发生在协议转换层的故障。

一个小小的信息丢失。

可能就会让 Agent 失去它最重要的能力。

## 工具调用是如何丢失的

为了真正理解 #3487，我开始尝试还原一次完整的调用过程。

以前我以为：

Agent 调用工具，就是发送一句：

“请帮我执行这个命令。”

但是实际上，Agent 和模型之间交流的，并不是简单文本。

它们交流的是一套协议。

例如，在 OpenAI 风格的工具调用中，一次工具请求可能类似这样：

```python
tool_request = {
    "role": "assistant",
    "tool_calls": [
        {
            "id": "call_001",
            "type": "function",
            "function": {
                "name": "execute_command",
                "arguments": '{"cmd": "ls -la"}',
            },
        }
    ],
}
```

这里看起来只是几个字段。

但是对于 Agent 来说，每一个字段都有意义。

`name` 告诉系统：

我要调用哪个工具。

`arguments` 告诉系统：

工具应该执行什么参数。

而 `id` 则负责连接：

“这一次请求”和“后面的工具返回”。

它们共同组成了一次完整的行动。

但是，当请求经过 CC Switch 时，事情变得复杂起来。

因为 Codex 使用的协议，和上游模型支持的协议，并不一定相同。

例如，Responses API 可能把调用表达为一个独立的响应项：

```python
responses_api_item = {
    "type": "function_call",
    "call_id": "call_001",
    "name": "execute_command",
    "arguments": '{"cmd": "ls -la"}',
}
```

Codex 可能发送的是 Responses API：

而另一个上游可能期待的是 Chat Completions 风格：

```python
chat_completions_message = {
    "role": "assistant",
    "tool_calls": [
        {
            "id": "call_001",
            "type": "function",
            "function": {
                "name": "execute_command",
                "arguments": '{"cmd": "ls -la"}',
            },
        }
    ],
}
```

看起来，它们表达的是同一个意思：

“调用 execute_command。”

但是对于机器来说：

字段不同。

结构不同。

语义绑定方式也不同。

所以协议转换层承担的任务，并不是简单复制字段。

它需要理解：

- 哪个字段代表工具。
- 哪个字段代表一次调用。
- 哪个字段需要保留。
- 哪个字段需要重新组织。

这也是为什么一个看似简单的问题，会导致如此奇怪的现象。

如果普通文本转换错误：

用户可能只是得到一句错误回答。

但是如果工具调用转换错误：

影响的是 Agent 的行动能力。

例如，如果转换层丢掉了 `tool_calls`：

```python
broken_message = {
    "role": "assistant",
    "content": "我可以帮你执行这个命令。",
    # tool_calls 字段在转换过程中丢失
}
```

如果 `tool_calls` 在转换过程中丢失。

那么上游模型收到的消息可能变成：

对于模型来说，它看到的世界就是：

“用户在聊天。”

而不是：

“用户给了我工具，我需要执行动作。”

于是，它自然不会调用工具。

因为从它的视角来看：

工具根本不存在。

这一刻，我终于理解了之前 Codex 的异常。

它不是不会思考。

它只是和自己的工具之间失去了连接。

就像一个工程师坐在电脑前，却发现键盘和鼠标突然消失。

大脑还在。

但是行动能力已经被切断。

# 项目背景介绍

这是一个基于ReAct范式的研究型Agent，主要是为了学习实际的项目开发，围绕真实的学习场景，我们每天都要手动的去arxiv或者github去寻找高质量的论文，但是内容大多参差不齐，而且需要自己深入论文去读取判断这个论文有没有价值，然后存入我们的zotero进行留存，我们需要根据下载的论文进行阅读，判断有没有可以借鉴的地方，一般我们都只需要阅读部分比如方法，看看框架模块设计有没有新意，看看实验的效果如何，消融效果怎么样，然后这其实是一个频繁需要重复劳动的场景，我可以利用Agent来优化我们这个过程，让他帮我们去搜索论文，帮我们总结论文哪些需要精读，这些论文大概都做了什么工作，效果如何，然后我们根据Agent总结的情况来进行提效。

# 项目功能说明

## Agent Loop 与 Provider 解耦

手写Agent loop循环这个核心基座，使用了ReAct作为我们的循环范式，因为我们可能需要更换不同的模型，不同的供应商，比如openai，anthropic，所以我们手写了Provider来吧模型的推理从loop中解耦，我们可以通过更换不同的provider来实现无痛切换。

## 事件流机制

然后在我们循环执行内部有多个关键节点，比如模型推理前后，工具执行前后，我们通过设立事件流来把模型和工具的输出推送到我们的消息订阅方，实现了一次推送，统一接收，就不用我们重复的写很多比如打印log还有一些输出的内容了。

具体事件流的实现我们先定义一些事件类型比如session开始和结束，工具执行之前和之后，然后我们写我们的订阅消息类，内部就是一个列表，然后定义一个变量去实例化这个对象，然后把我们的订阅者通过内部类的方法来写入这个对象，然后emit就是循环调用订阅函数来实现消息传递。

## State上下文管理与压缩

然后我们Agent随着任务的执行，不出意料的上下文会开始变得拥挤，有很多与我们目标无关的中间内容来影响模型进行判断，所以我们通过State显示的把任务执行情况，当前执行的阶段，已经使用的工具，下一个需要使用的工具，是否达到目标，还剩余的预算来让模型可以实时了解目前的任务情况。

然后我们上下文每一次循环都需要构建我们的state，所以我们需要装配我们上下文，然后我们每次装配完上下文，我们需要提前判断我们上下文窗口的预算情况，如果达到我们设定的阈值比如80%我们需要主动进行压缩。

具体的压缩策略就是：

1. 首先我们的toolresult会先进行offload，去持久化放入磁盘，然后用地址作为占位符进行替换，在减轻上下文负担的同时，模型如果需要再次查看工具结果也不会丢失信息。

2. 然后就是大模型摘要压缩，我们通过把过去N轮的消息用模型输出一个摘要然后进行内容的替换。

3. 最后如果压缩之后还是不行，我们就进行硬阶段，这样的清理效果最好，但是副作用也是最高会丢失信息。

# 工具系统设计

然后我们Agent想要实现搜索论文，然后写入我们本地硬盘，都需要工具，所以我们实现了具体的工具。

然后我们给工具按照实际的作用进行分类，分别有：

- 感知类：只做查询操作。
- 执行类：代表有写入操作的工具。
- 协作类。

设立这些类型的原因是方便我们后面进行对应的权限管理。

## 工具执行保护

我们工具的执行不能过于乐观，工具执行前后都需要进行程序化的判断，所以为了方便这个过程我们通过统一的执行类来对我们的工具执行进行保证包括了执行前和执行后。

执行前：

- 参数校验，判断参数是否没有错误。
- 权限判断，判断我们这个工具是不是执行类是否需要HITL让用户进行监督判断。

工具执行之后：

- 判断工具的输出结果是不是符合我们的输出要求。

然后工具有可能是用的远程API，也有可能用的MCP远程服务器所以我们需要try catch捕获可能的网络问题，我们进行指数退避的重试，还有多次工具调用错误还需要降级和fallback。

# Context工程设计

然后我们上下文内部不只是有我们的动态需要压缩管理的轨迹，也有比如主动放入的文档和被动召回的相关内容。

就比如我们给我们agent写的一个md文档里面包含了我们对于agent的约束，比如他不能进行哪些操作，然后我们对于特定工作流的偏好，比如搜索论文如果arxiv关键词搜索不到，我们需要从CVF官网上搜索。

为什么选择md全量注入的原因：

- 比向量化的信息，就是他是可视化的。
- 可以版本管理进行迭代。
- 他是准确的内容。

但是对于我们研究型我们很多时候需要语义相关性匹配，比如我们对于某些研究有些疑问然后口语化的让模型处理，这个时候精确的匹配比如grep就效果不好，所以这个时候需要语义相似度匹配，所以需要RAG。

# RAG系统设计

## PDF转换与分块

我们项目内部会把下载的pdf通过pymupdf进行转换成md类型，然后我们使用固定大小还有递归字符分割进行分块。

## Embedding模型选择

嵌入模型选择了API使用了bge-m3多语言模型。

选择原因就是论文不止有英语环境的也有很多中文环境的，我之前还测试过如果使用中文的bge版本他很难映射到合适的向量空间导致效果很差。

而且如果我们用户的提问如果是中文的，我们用英语语言的嵌入模型，我们很难召回到相关内容，这也是我用多语言模型的原因。

# 混合检索

然后内部使用了混合检索：

- bm25作为稀疏检索。
- Embedding作为稠密检索。

我们通过分词器对于我们的块进行分词生成词表。

具体就是一个词然后后面是他对应的文档块以及出现的次数，然后还有IDF分数也就是逆文本。

其实就是一个词在其他文档的次数越少就代表越稀有，所以分数更高。

然后我们用户提问进来也会先分词，然后根据每个词去计算每个块的分数然后输出一个排名。

我们用rrf排名来进行分数融合：


具体原因是不同的检索的分数量纲不一样，稀疏的分数通常更大，所以用排名更公平。

# Reranker重排序

然后我们检索之后的topk个内容的效果因为用的bi-encoder虽然速度很快而且可以离线构建，但是实际的效果不好。

所以我们需要用cross-encoder进行重排。

具体就是把问题和文档块一起送入模型进行注意力计算。

对比单独进行嵌入，他可以让问题和文档进行深度的交互，所以可能显著提高召回情况。

---

# GraphRAG论文关系检索

然后我们RAG解决的语义之间的相似性和关键词像是数字和专有名字的准确匹配。

但是对于我们论文中的引用这个场景，他无法知道我们这个论文和其他论文的一个关系。

所以我们需要构建GraphRAG。

流程：

1. 先用大模型抽取我们的实体和关系。
2. 给他们构建关系图。
3. 使用社区聚类算法，给我们的图数据按照主题分成不同的族群。
4. 检索时进行多跳查询，可以知道不同论文之间的关系。

对于我们论文的这种引用查询非常不错。

# Multi-Agent并行执行

然后对于我们比如总结多个不同的论文，我们顺序的一个一个总结不仅效果不好而且工作中间的上下文会影响我们总任务。

所以利用sub agent作为一个工具。

当模型判断需要同步执行多个任务的时候：

- 创建多个会话。
- Fan-out执行工作。
- 内部就是干净的loop。
- 只返回最后的结论给我们的主Agent。

实现高效的任务执行以及更良好的上下文空间。

然后为了防止任务冲突，我们通过git worktree让每个agent都有自己的一个操作空间。

---

# 输出验证机制

然后模型是否完成我们设定的目标不能只看他自己输出，要根据真实的输出情况。

比如coding agent可以用单元测试的方式来验证代码有没有编写成功。

所以我们也需要通过一个验证器来验证模型的输出，从而防止模型幻觉来编造论文。

尤其是对于引用参考的部分，我们通过工具来让模型对于涉及的论文进行交叉验证判断是不是真实存在的，来进行结果验证。
